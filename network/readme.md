# 네트워크 모음집

## OSI 7계층
- 응표세전네데물, 즉 응용/표현/세션/전송/네트워크/데이터링크/물리 등의 7가지 계층으로 나뉘어져 있다.

### 응용 계층
- 사용자가 네트워크 서비스에 접근할 수 있게 해주는 최상위 계층.
- 역할: 사용자에게 네트워크 서비스와 UI를 제공한다.
- 주요 프로토콜
  - HTTP(Hypertext Transfer Protocol): 웹 브라우저와 서버 간 데이터를 주고받을 수 있게 만드는 프로토콜.
  - DNS(Domain Name System): 웹의 도메인 주소에 대응하는 실제 IP 주소를 찾아주는 프로토콜.

### 표현 계층
- 데이터를 어떻게 표현할지 결정하는 계층.
- 역할: 데이터를 인코딩/디코딩, 암호화/복호화, 압축한다.
- 주요 프로토콜
  - SSL/TLS: 데이터를 안전하게 전송하기 위한 암호화 프로토콜.
  - JPEG/MPEG: 이미지/영상 인코딩에 대한 표준.

### 세션 계층
- 컴퓨터의 연결(세션)을 설정, 관리, 종료하는 계층.
- 역할: 통신 세션 유지, 동기화, 복구 등등, 통신 장치들 간 상호작용 제어.
- 주요 프로토콜
  - RPC(Remote Protocol Call): 별도의 원격 제어를 위한 코딩 없이 다른 주소 공간에서 함수나 프로시저를 실행할 수 있게 만드는 프로세스 간 통신.
  - NetBIOS: 로컬 영역 네트워크 내에서 컴퓨터들이 서로 통신을 주고받게 해줄 수 있는 서비스.

### 전송 계층
- 양 끝단(End-to-end)의 사용자 간 신뢰성 있는 데이터를 주고받게 해주는 계층.
- 역할: 데이터 분할 및 재조립, 오류 검출 및 복구, 흐름 제어 등등.
- 주요 프로토콜
  - TCP(Transmission Control Protocol): 3-way handshake를 통해, 연결 지향적이며 신뢰성 있는 통신을 보장하는 프로토콜.
  - UDP(User Datagram Protocol): 비연결 지향적이고 신뢰성보다 속도를 지향하는 프로토콜.

### 네트워크 계층
- 데이터를 목적지까지 가장 안전하고 빠르게 전송하는 계층.
- 역할: 데이터가 목적지까지 가는 경로 선택(라우팅), IP 주소 지정, 패킷 전달.
- 주요 프로토콜
  - IP(Internet Protocol): 호스트 주소 지정 및, 패킷 분할 및 재조립.
  - ICMP(Internet Control Message Protocol): ping 등, 네트워크 내 오류 보고 및 상태 확인.

### 데이터 링크 계층
- 물리적인 연결을 통해 두 장치 간의 신뢰성 있는 정보 전송을 보장하는 계층.
- 역할: 물리(MAC) 주소 지정, 프레임 동기화, 오류 검출.
- 주요 프로토콜
  - 이더넷(Ethernet): LAN 환경에서 가장 많이 쓰이는 유선 네트워크 기술.
  - Wi-Fi(802.11): 무선 LAN을 위한 표준 규격.

### 물리 계층
- 데이터를 전기적 신호로 변환하여 케이블 등의 실제 매체로 전송하는 계층.
- 역할: 비트(Bit) 단위의 데이터 전송, 기계적/전기적 특성 정의.
- 주요 프로토콜
  - RS-232, RJ-45: 케이블 및 커넥터 규격.
  - 리피터, 허브: 전기 신호를 증폭하거나 전달.

## TCP 통신과 UDP 통신의 차이
- TCP 통신
  - TCP 통신은 서버와 클라이언트가 서로 데이터를 전송하기 전에 3-way handshake를 통해 서로 연결되었는지 확인한다.
    - 근데 왜 3-way handshake지?
      - 수신측과 송신측 모두 서로 통신할 준비가 완료되었음을 확인해야 하기 때문이다.
  - 그 다음, 데이터를 전송하는 동안, 수신 측으로부터 보낸 ACK 패킷을 통해 데이터가 잘 전송되었는지 확인한다.
  - 이 프로토콜이 사용되는 곳은, 웹 서비스나 이메일이나 파일 전송같이, 데이터가 오류 없이 잘 보내져야 하는 곳에 쓰인다.
- UDP 통신
  - UDP 통신은 서버와 클라이언트가 서로 연결되었는지 확인하지 않는다.
  - 데이터를 전송하는 동안에도, 데이터가 잘 보내졌는지 확인하지 않는다.
  - 이 프로토콜이 사용되는 곳은, 실시간 온라인 게임이나 동영상 스트리밍같이, 정확성보다 속도가 우선시되는 곳에 쓰인다.

## HTTP와 HTTPS의 차이
- HTTP
  - 평문으로 데이터를 전송
  - 80번 포트를 기본으로 사용한다
  - 전송되는 데이터가 그대로 노출될 위험이 있다
- HTTPS
  - SSL/TLS를 통해 암호화시킨 데이터를 전송
  - 443번 포트를 기본으로 사용한다
  - 전송되는 데이터의 기밀성, 무결성, 인증을 제공한다.

## HTTP 메소드
- GET: 데이터를 불러온다.
- POST: 새로운 데이터를 등록한다.
- PATCH: 기존에 있던 데이터의 일부를 교체한다.
- PUT: 기존에 있던 데이터를 완전히 덮어씌운다.
- DELETE: 데이터를 제거한다.
- OPTIONS: 특정 URL에서 사용할 수 있는 HTTP 메소드들을 확인한다.
  - 이를 통해, 통신을 시작하기 전에, 사용 가능한 메소드들을 응답 헤더의 Allow 영역을 통해 미리 알아볼 수 있다.
  - CORS Preflight가 가장 큰 목적.

## HTTP 응답 상태 코드
- 100번대: 진행 중 정보 제공
- 200번대: 성공적인 결과 (대표적으로 200 OK, 201 Created 등등)
- 300번대: 리다이렉션 등의 추가 조치 필요
- 400번대: 사용자 측 오류 (대표적으로 404 Not Found, 403 Forbidden 등등)
- 500번대: 서버 측 오류 (대표적으로 502 Bad Gateway 등등)

## REST API
- REST API는 서버 자원을 URI로 식별하고, 그 자원에 대한 행위를 GET, POST, PUT, DELETE 등의 HTTP 메서드로 표현하는 규칙 기반의 API 설계 방식.
- RESTful API의 6대 기본 원칙
  - 클라이언트-서버 구조 (Client-Server Structure)
    - 클라이언트와 서버는 독립적이어야 하며, 클라이언트는 오직 URI 리소스만 알아야 한다.
    - 둘의 인터페이스가 변경되지 않는 한, 둘은 서로 독립적으로 개발되어야 한다. (관심사의 명확한 분리)
  - 무상태성 (Stateless)
    - 서버는 클라이언트로부터 받는 요청이나 클라이언트의 어떤 상태도 저장해선 안 된다.
    - 클라이언트의 모든 요청은 그 요청을 이해할 수 있는 모든 정보를 포함해야 한다.
      - 컨텍스트를 유지해야 하는 세션이나 인가/인증 정보도 클라이언트에서 저장되며, 클라이언트는 서버에 요청을 할 때마다 이 정보들을 모두 포함하여 보낸다.
  - 캐시 가능성 (Cachable)
    - 서버는 응답의 cache-control 헤더에 해당 요청에 대한 응답을 캐시할 수 있는지 여부를 알려줘야 한다.
    - 이를 통해, 클라이언트는 응답을 캐시하여 서버와의 상호작용을 최소화하고, 서버의 성능과 가용성을 최대화할 수 있게 된다.
  - 일관된 인터페이스 (Uniform Interface)
    - 요청에 어떤 개별 자원을 식별할 수 있는지 (Identification of resources), 그 자원에 대해 어떤 연산을 진행할 것인지 (Manipulation of resources through representations), 자기 자신을 어떻게 처리할 것인지 (Self-descriptive messages), 결과에 대해 어떤 정보를 받을 수 있는지 명시되어야 한다 (Hypermedia as the engine of application state).
  - 다중 계층 구조 (Layered System)
    - API 서버, DB 서버, 인증 서버를 따로 두는 등, 서버가 여러가지 계층을 가질 수 있도록 허용해야 한다.
    - 각 계층의 서버는 자기가 통신하는 계층 이외의 서버의 정보를 알 수 없다.
    - 클라이언트는 API 서버에만 직접 접근할 수 있고, 그 외 (DB 서버나 인증 서버같은) 계층의 서버에는 직접 접근할 수 없으며, 그들의 상호작용이나 정보 또한 알 수 없다.
  - Code on demand
    - 서버가 클라이언트에게 실행할 수 있는 로직을 전송하여 클라이언트의 기능을 확장시킬 수 있다.
    - 이를 통해, 클라이언트는 사전에 구현해야 하는 기능의 수를 줄여 간소화시킬 수 있게 된다.
